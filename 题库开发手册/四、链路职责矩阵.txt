链路职责矩阵
================================================================
版本：v1（已确认）｜ 2026-09-18 23:30 ｜ 状态：产品负责人逐条确认（11/11）
说明：本文档原为"待确认草案"，经产品负责人逐条勾选确认后转为**生效口径**。
      文中的 B1–B3、产出 1–6、W1–W3、S1–S4 与第八节的实现顺序均为已确认内容；
      后续实现若与本矩阵冲突，以本矩阵为准。
目的：把"谁产什么、谁消费什么"定死，消除三条产线之间的错位、重复与浪费。
范围：题目完善（question_enrichment）、AI 巡检（知识分类 Agent 1-3）、知识档案（knowledge dossiers）、
      裁决台（题目编辑/审核入口）、金标（盲测基准）。不含学生端功能本身。


零、先确立三条不可动摇的边界
----------------------------------------------------------------
B1. AI 只产"建议"。任何 AI 产出都不得自动写入正式数据；必须经人工裁决。
B2. 正式数据是学生端（复习、错题推送、目录投影）读取的唯一来源。
    建议、参考关联、相似族、金标，一律不参与学生端的筛选与统计。
B3. 算法不合并、流程统一。三条产线保留各自提示词/模型/调度；但共用同一套
    "建议 → 逐字段采纳 → 落正式数据"的骨架（复用题目完善既有的
    status: recommended → applied / rejected、appliedFields、appliedVersion 词汇）。


一、三层角色
----------------------------------------------------------------
产线层（建议的制造者，可独立运行、可重跑、可跳过）
  · 题目完善：目录位置、知识点、结构化得分点
  · AI 巡检：作答核心、最小充分知识集、问题知识范围、考查动作、题族裁决、逐选项知识
  · 知识档案：知识点条目（定义、纳入/排除边界、教材锚点）

裁决层（唯一的写入权威，唯一的人工入口）
  · 裁决台：逐字段采纳/驳回/就地修正，记录来源与版本

基准层（只测量，不生产、不进学生端）
  · 金标：冻结基准 + 回放打分


二、职责矩阵（现状 → 目标 → 迁移代价）
----------------------------------------------------------------
【产出 1：目录归属】
  现状：题目完善产出目录，并被当作"归类主依据"；文学史中目录与题族恰好重合，掩盖了问题。
  问题：现代汉语里"一层目录下挂多个题族"（如 目录 语音>辅音与声母 ↔ 题族 声母发音方法·声带振动），
        目录无法承担归类职责 → 匹配结果过时/浪费。
  目标：目录**降级为溯源信息**（这道题的原文出自教材哪一章），可自动带出；归类一律以题族为准。
  迁移代价：低。题目侧保留目录字段只作展示与溯源；归类判定不再读它。
  风险：无（不删除已有数据）。

【产出 2：知识点】
  现状：题目完善产出"知识点"写入题目；AI 巡检又独立算一套 requiredNodeIds → 两套并存、互相打架。
  问题：两者不是一回事却被当成同一件事。
  目标：区分两个概念——
        (a) 题目的必需知识（作答要懂什么）→ 归 **AI 巡检 → 正式指纹 requiredNodeIds**；
        (b) 知识点/概念条目（学科上可复习的概念及其定义与边界）→ 归 **知识档案**。
        题目完善**退出**"知识点"这一项。
  迁移代价：中。需保留历史值（不删），只停止新产；裁决台不再把"完善产出的知识点"写进题目字段。
  风险：中。若历史题目已写入该字段，需明确"旧的仅作展示，不再作为判定依据"。

【产出 3：教材证据】
  现状：题目完善、AI 巡检、知识档案**各自检索一遍**，口径与结果可能不一致
        （曾出现"一边给出教材 298 页、另一边称未找到"）。
  问题：重复劳动 + 口径冲突。
  目标：**同一道题、同一本书、同一套检索规则只检索一次**，结果作为共享产物供三条产线消费。
  迁移代价：中高。需抽出一个共享的证据检索产物（可缓存），三条产线改为消费它。
  风险：中。短期可先"共享结果"，长期再统一检索参数。

【产出 4：结构化得分点 / 答案质疑】
  现状：题目完善产出，归属正确。
  目标：保持不变（这是题目完善的本职）。
  迁移代价：无。

【产出 5：题族与题族边界】
  现状：题族的 inclusionBoundary/exclusionBoundary **全空**；巡检被迫自己猜范围。
  问题：边界本不该由巡检产出。
  目标：边界由**知识档案**产出（档案已有 inclusionCriteria / exclusionCriteria），
        题族**引用**档案的边界，而不是每族重写。
  迁移代价：中。需建立"题族 → 档案"的引用关系。
  风险：中。已有 100 个族需逐步挂接。

【产出 6：逐选项知识（选项 → 知识关系 / 涉及知识）】
  现状：仅存在于金标审核条目（68/80 条），正式指纹与分类结果里都没有 → 编辑页看不到、学生端用不上。
  目标：作为**正式知识指纹的一部分**（沿用既有形状与协议版本 option-knowledge-v2）；
        "是否纳入问题知识范围"**复用既有 problemKnowledgeRangeNodeIds**，不新增字段；
        跨主题节点因锚点硬校验自动无法纳入（正好实现"标注可跨主题、纳入受主题约束"）。
  迁移代价：中。新增字段挂载 + 写入路径 + 由金标既有 68 条回填。
  风险：低（复用既有协议，不发明新概念）。


三、三类浪费的具体清单（供逐条确认）
----------------------------------------------------------------
W1. 目录被当作归类依据 → 建议：降级为溯源。
W2. 题目完善产"知识点"、巡检又产一套必需知识 → 建议：前者退出，后者为准；概念条目归档案。
W3. 教材证据三条产线各检索一遍、口径可能冲突 → 建议：只检一次、共享结果。


四、流程统一的形态（不含算法合并）
----------------------------------------------------------------
每道题 = 一条工作流：
  待处理 ──┬── 工序 A：题目完善（可跳过、可重跑）
           └── 工序 B：AI 巡检（可跳过、可重跑）
                        │
                        ▼
              裁决台（唯一入口；逐字段采纳/驳回/就地修正；标注来源；留痕 appliedFields/appliedVersion）
                        │
                        ▼
              正式数据（题目字段 + 正式知识指纹）← 学生端唯一来源
                        │
                        │（仅当该题在金标批次内）
                        ▼
              金标 = 挂在流程外的测量装置（冻结基准、回放打分）


五、金标与正式数据的同步规则（建议）
----------------------------------------------------------------
S1. 裁决台改动正式事实后，若该题在金标批次内 → 系统标记"基准已过期"，提示重新冻结/重校准。
S2. 金标侧改动 → 反向提示"正式题与基准不一致"。
S3. 二者是同一事实的两个视图，一致性由系统保证，不靠人工两头核对。
S4. 不采用"自动同步写回"：基准一旦被静默改写，测量即失去意义。


六、明确不动的东西（避免误伤）

· 题目完善的得分点/答案职能：保持。
· 已有历史数据：不删除，只停止新产或降级用途。
· 学生端读取口径：仍然只读正式数据的必需层。

【二、接口设计（新端点）】
  GET /api/admin/adjudication/queue
    参数：bookId（取工作区当前教材，不再有 all）/ source（all|question_enrichment|knowledge_inspection）
          / status（all|recommended|applied|rejected）/ query / page / pageSize
    返回：{ success, page, pageSize, pageCount,
            summary: { total, recommended, applied, rejected,
                       bySource: { question_enrichment: n, knowledge_inspection: n } },
            items: [{ id, source, questionId, questionStem, bookId, status,
                      fieldLabels, targetType, reviewedBy, reviewedAt, updatedAt,
                      appliedFields, appliedVersion }] }
  【合并规则，写死】两边各取**全量** → 按 updatedAt 倒序 → 同一时间戳按 source、再按 id 稳定排序
                    → 最后分页。禁止"各自分页再归并"（会出现第 2 页比第 1 页新）。
  【性能】现有上限：完善建议 5000 / 巡检结果 10000。先按全量实现并实测耗时；慢了再上游标。

【三、界面】
  · 裁决台面板（与 #knowledge-inspection-panel 同级，复用现有页壳与筛选风格）：
    筛选行（来源 / 状态 / 搜索 / 刷新）→ 汇总条（待处理 N（完善 a · 巡检 b）· 已采纳 c · 已驳回 d）
    → 列表项（来源徽标 + 题目 + 涉及字段 + 状态 + 时间 + 「去裁决」）。
  · 「去裁决」跳转：题目完善 → 完善题目子标签并定位该题；AI 巡检 → AI 巡检子标签并定位该结果。
  · 「完善题目」子标签 = 现有题目完善页内容**原样搬入**，不重写内部结构、不改语义。
  · 两个新面板都不需要左侧教材知识树（与 AI 巡检同一处理：隐藏知识树、内容区占满宽度）。

【四、"唯一人工入口"的约束方式（产品负责人问，答复为建议并获认可）】
  · **要强约束，但先建后切**：
    - 现在不切：裁决台尚未建，先关掉两页的采纳按钮会暂时削弱裁决能力（等于"能看不能用"）。
    - 切换条件（可验证，不看时间）：把现有两页当前可裁决的字段/动作**逐项对照**，裁决台缺一项就不切，
      并配端到端断言。切换后各产线页的采纳动作降级为"跳转到裁决台"。
    - 切换之前：各产线页的采纳按钮保留，但加来源标注（"该建议也会出现在裁决台"）。
  · **要给第三条产线（知识档案）留位，但只留"结构位"**：
    - 留：来源筛选按数据动态渲染，界面不写死"只有两个来源"；排序/分组规则不假设来源数量。
    - 不留：**不往共享词汇表（suggestion-lifecycle.js）加 knowledge_dossier 这个值** ——
      加了就是没人产生、没人消费的死词，将来真做时还得改。
