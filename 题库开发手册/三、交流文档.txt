## 2026-09-20｜约定：原生 `button`（分享等开放能力）不要直接当排布项

- 发起人：Codex（自本轮 bug 复盘）
- 负责人：Codex
- 状态：已确认为实现约定
- 新增决议：无（实现细节约定）

**问题**：抽屉里「分享卡集」需要原生 `<button open-type="share">`。把它**直接作为 grid 项**放进 `.drawer-grid` 后，即便用类名覆盖了 `margin/padding/border/background`，微信 `button` 自带的盒子（默认宽度/行高/`::after` 伪元素）仍会让这一格内容偏离列，表现为“这两个条目跑到第 2、3 列，和下面几行对不齐”（产品负责人截图框出的正是这一处）。

**约定**：需要开放能力的按钮（`open-type="share"` / `getUserInfo` / `contact` 等）**只做触发，不做布局**：

1. 用普通 `<view class="...">` 承担布局（参与 grid/flex，列宽、间距、基线与其他项一致）；
2. 在它内部叠一个**铺满且透明**的原生按钮负责触发：
   `.host{position:relative}` + `.trigger{position:absolute;top:0;right:0;bottom:0;left:0;width:100%;height:100%;margin:0;padding:0;background:transparent;border:none;border-radius:0;opacity:0}` + `.trigger::after{display:none;border:none}`；
3. 已按此改写的例子：`apps/miniprogram/pages/card-box/card-box.wxml` 的「分享卡集」（`.drawer-item-share-host` + `.drawer-share-trigger`）。卡集页底栏的历史写法（`button.float-share` 直接参与 flex）在新页面上不要再复制。

## 2026-09-20｜约定：带遮罩的瞬态浮层必须随页面离开自动关闭

- 发起人：产品负责人（"这个长按工具栏不应该是离开某个页面就自动关闭吗"）
- 负责人：Codex
- 状态：已确认为全仓库约定并落地
- 新增决议：无（属缺陷修复 + 跨 Agent 约定，不新增产品决议）

**问题**：长按弹出的工具栏都带一张全屏遮罩，`z-index` 往往高于页面所有按钮（题库页那两张是 1700/1800，连底部胶囊导航都被盖住）。若遮罩是**全透明**且不拦 `touchmove`，一旦跨页残留就是「页面能滚、点哪儿都没反应」的隐形拦截层——而且肉眼完全看不出来。

**约定（所有页面、所有 Agent 遵守）**：

1. **瞬态浮层（长按工具栏 / 抽屉 / 菜单 / 选择器 / 详情层）必须随页面离开自动关闭**：页面加 `onHide` 收掉它们；Tab 页额外在 `onShow` 开头也收一次（跨 Tab 回来不能一进来就被遮住）。
2. **遮罩不允许用 `background: transparent`**：至少给一层极浅底色（如 `rgba(21,30,25,.08)`），万一有浮层没关掉，界面上能立刻看出来，而不是静默拦截。
3. 统一走公共方法 `apps/miniprogram/utils/page-layers.js` 的 `closeTransientLayers(page, keys, extra)`（只清真正处于打开状态的标志，避免无意义的 setData）。
4. 已接入页面：analysis、card-box、card-editor、card-set、home、knowledge、knowledge-card、library、note-editor、pack-collection、practice、review、wrong-book。`tests/page-transient-layers.test.js` 会遍历 `app.json` 注册的页面：凡渲染了 `wx:if="{{xxxOpen}}"` 浮层却没接 `onHide` 的会直接测试失败——以后新增页面也被这条守住。
5. 已下线、未注册进 `app.json` 的页面（`pack-detail`）不参与该约定。

## 2026-09-18｜浅色板取色原则与"上色卡片不加灰边"

- 发起人：产品负责人（反馈卡片颜色"发暗、脏脏的"）
- 负责人：DeepSeek
- 状态：已确认并实现
- 关联决议：DEC-067 / DEC-068 的视觉修正

现象：同一批浅色底，放在本产品里比参考小程序显得暗沉。原因不是"饱和度太低"，而是三件事叠加：

1. **色相没校准**：原色板里 `#DAEEDA`（薄荷）红蓝分量相等、色相正好 120°，是灰绿/鼠尾草绿；`#F7DEDE`（浅粉）色相 0° 且彩度低，看着像灰玫瑰。
2. **上色卡片还带暖灰描边**（`1rpx solid #ece6de`），等于给浅色块镶了一圈灰边。
3. **页面底色是暖米色**（`#f8f6f3`），会给浅色蒙一层灰纱。

**取色原则（后续新增颜色照此办理）**
- 明度统一 ≈ 92%，**色相校准**（薄荷走 130–140° 偏青，浅粉走 350° 偏冷），彩度略提；
- `accent`（小字与进度条）加深加纯，避免小字发灰；
- 现色板（相对亮度 0.75–0.86）：浅粉 `#FBD9E0` / 蜜桃 `#FDE0CE` / 奶油 `#FBEEC4` / 薄荷 `#D8F2DE` / 浅青 `#D2F1EC` / 鹅黄 `#FCECAC` / 天蓝 `#D5ECFA` / 浅蓝 `#D9E5FB` / 浅紫 `#E3DAFA`。**这套是定稿值**，不要再整体提亮（提亮那一版被判定为过亮）。

**其它修正**
- 上色卡片去掉暖灰描边（`.set-tinted` / `.study-card-tinted` → `border-color:transparent`），白底卡片保留描边以区分背景；
- **玻璃/水晶质感（卡面定稿做法）**：卡面 = **四层光/暗 + 浅色**，由 `cardColorBackground()` 生成：
  1. 主高光 `linear-gradient(150deg, rgba(255,255,255,.42) → .12 → 0)`（**弱而收**，只到 58% 就消失）；
  2. 镜面亮点 `radial-gradient(18% 12% at 76% 9%, rgba(255,255,255,.95) 0%, rgba(255,255,255,.34) 34%, rgba(255,255,255,0) 62%)`（**小而锐、带中间停靠点**，这是"玻璃"而非"塑料"的关键）；
  3. 底部透光 `linear-gradient(0deg, rgba(255,255,255,.22) → 0 20%)`；
  4. **背光侧折射暗部** `linear-gradient(336deg, <accent 12%> → 0 42%)`（同色系而非白色，做厚度）；
  5. 浅色本体。
  再叠加 **CSS inset 光**：顶（`.9`）/左（`.5`）/底（`.3`）各一条 2rpx 白色内描边，加右下 `inset -10rpx -14rpx 26rpx -18rpx var(--card-edge,rgba(0,0,0,0))` 的同色暗部（白底卡片因回退值而自动跳过）。
- **"塑料感"的根因与解法**：早期版本只有一大片**白色**柔光、没有任何暗部——那是塑料壳的特征。玻璃/水晶需要 ① 小而锐的镜面点；② 边缘一圈亮线；③ **背光侧同色系暗部（厚度/折射）**。三者缺一就偏塑料。
- **真机教训：高光峰值不能贴边**。最初峰值 `.72` 起于 0%、镜面点贴右上角，真机上左上角/上边缘被"洗白"，与近白背景连成一片，看起来像边缘糊了。修正：峰值降到 `.55`、镜面点挪到 78%/12%，并且**给上色卡片一圈同色系玻璃边**（`cardColorEdge()` = accent 26% 透明度的 `rgba`），把边缘重新框出来。
- **边框色用自定义属性下发**：行内只写 `--card-edge`，样式表里 `.set-tinted{border-color:var(--card-edge)}`。**不要**把 `border-color` 直接写进行内样式——行内优先级最高，会盖掉选中态的 3rpx 蓝框（`.set-tinted.set-selected{border:3rpx solid #2f9fff}` 靠 class 特异度取胜）。
- **不使用 `backdrop-filter`**：卡片底色是不透明的，模糊没有可透的内容；且部分安卓 WebView 支持不稳，用分层渐变即可达到同样观感。
- **不使用投影**：全部用 inset 光表达"光"，符合"卡片不加投影、投影只留给底部悬浮栏"的既定口径。
- **亮度旋钮（供后续微调）**：① 高光占比（`.92 / .46` 两个停靠点）；② 浅色本身的明度（当前 soft 的相对亮度在 0.79–0.89 之间，越接近 1 越亮、但色相也会越淡）；③ 页面底色（当前 `#fdfcfa`，可到纯白但会让背景装饰圆弧看不见）；
- 页面底色 `#f8f6f3` → `#fdfcfa`（更接近白，仍在暖灰一侧），卡集页底色一并从灰绿 `#f4f6f4` 对齐到 `#fdfcfa`；
- 卡片圆角 20rpx → 28rpx（卡集页 8rpx → 20rpx），接近参考图的圆润度；
- 上色卡片上的次要文字改用中性灰（`#8d938f`）而不是暖灰 `#8b8478`；
- 定位高亮 `.card-flash` 改为**内描边**表达（上色卡片的底色是行内样式，`background` 会被盖掉，看不到定位效果）。

## 2026-09-18｜图标配色约定：白色 pack-* 只用于深色表面

- 发起人：产品负责人（截图反馈抽屉图标缺失；随后指出操作栏里的调色板图标应为白色）
- 负责人：DeepSeek
- 状态：已确认并实现
- 关联决议：无（约定类）

**命名规则（全产品统一）**

| 图标文件 | 含义 | 只允许出现在 |
| --- | --- | --- |
| `pack-*.svg`（`stroke="#ffffff"`） | 白色系 | **深色表面**：黑色操作栏、选择栏、深色菜单、深色面板 |
| 其他 `*.svg`（深色描边 + 少量彩色） | 深色系 | **浅色表面**：白底抽屉、面板、列表、表单 |

- 同一语义需要两套时，白色版叫 `pack-<name>.svg`，深色版叫 `<name>.svg`（例如 `pack-palette.svg` / `palette.svg`）。`pack-close` 的深色对应 `x.svg`；重命名 / 删除 / 移动等深色版用 `card-rename` / `card-delete` / `card-move`。
- 判断依据是**直接或祖先容器的 class token**：深色容器 token 为 `context-toolbar` / `selection-toolbar` / `context-menu` / `add-menu`；浅色容器 token 为 `drawer-layer` / `more-drawer` / `color-panel` / `catalog-panel` / `directory`。
- `tests/icon-surface-convention.test.js` 把这条规则变成**自动检查**：① 深色表面出现深色图标即失败；② 浅色抽屉/面板出现 `pack-*` 即失败；③ 引用了不存在的图标即失败；④ 每个 `pack-*` 必须有对应深色版。
- 当天因这条规则踩了三次坑（抽屉里白图标隐形、抽屉里缺 `pack-*`、操作栏里用了深色调色板图标），所以这次不只补图标，还把规则测住。

**更彻底的方案（未采纳，留作备选）**：图标改用 `-webkit-mask-image` + `background-color: currentColor`，一个文件跟随 CSS 变色。能根治“同一语义两份文件”，但要改动全部 `<image>` 用法，且部分安卓 WebView 对 mask 支持不稳，风险大于收益。

## 2026-09-15｜卡集深色弹窗菜单与长按拖拽排序

- 发起人：产品负责人
- 负责人：Codex
- 状态：已确认并实现
- 新增决议：DEC-051、DEC-052

**深色弹窗菜单（DEC-051）**：卡集页操作栏里的“添加 / 标题级别 / 移动 / 移动到目录 / 相对于卡片新增”不再调用微信系统 ActionSheet，统一改为与黑色操作栏同一视觉的深色圆角菜单。菜单出现在操作栏正下方，横向按操作栏对齐方式（多选跟随所选卡片所在列、目录整理居中）对齐；条目超过剩余高度时在菜单内部滚动；点条目执行并关闭，点菜单外关闭。多选时“移动到目录”直接列出全部目录（可滚动），不再按目录数量切换成输入框。

**长按拖拽排序（DEC-052）**：长按卡片或目录标题后继续移动手指（超过约 10px）进入拖拽；只长按不移动仍然进入多选 / 目录整理，不误触发拖拽。拖拽中被拖元素抬起跟随手指、操作栏自动隐藏，页面仍可滚动且落点按当前滚动实时校正。插入位置固定用蓝色提示条表达：

- 落在某一行两列**中间**：左侧卡片右边缘显示竖向蓝条，表示插到这两张卡片之间；
- 落在某一行**最前方**或整段**末尾**：该行上方或末行下方显示贯穿内容宽度的横向蓝条；
- 落在空目录上：目录标题下方显示横向蓝条。

松手即按提示条落位：卡片可以在同一目录内换位，也可以直接拖入其他目录；目录拖拽只调整顺序、不改变标题级别，子目录随父目录整体移动；拖拽不新增或删除任何卡片与目录。本轮只移动被拖的那一张卡片，多选状态下不会整批移动，如需要整批移动再单独提口径。

**拖拽期间冻结页面滚动（实测补充）**：产品负责人实测发现拖拽时页面有时会跟着卡片一起滚动、观感很卡。原因是长按后手指移动会同时驱动页面滚动。按微信官方推荐方式，在页面首个节点加 `<page-meta page-style="{{pageScrollLocked ? 'overflow: hidden;' : ''}}" />`。第一版把锁定时机放在“拖拽真正开始（移动超过 10px）”，实测仍然卡——因为原生滚动手势一旦被识别，之后再设 `overflow:hidden` 也停不下来，这个滚动会伴随整个拖拽。最终口径改为：**长按触发的瞬间（手指还没移动时）就锁定页面滚动**，手指抬起（touchend/cancel）立即恢复。这样拖拽全程不会产生任何页面滚动，被拖元素严格跟随手指；只长按不拖拽时抬手后照常可以滚动，多选浏览不受影响。落点仍按当前滚动位置实时校正，保证提示条与落位一致。

**旧工具栏样式清理**：`card-set.wxss` 中的 `.selection-toolbar` / `.selection-left|center|right`（早期 4 项多选胶囊，图标用 CSS 背景图实现）与 `.directory-actions`（早期贴底白色菜单 → 贴底黑色四项胶囊 → 吸顶胶囊三代覆盖）共 23 条规则已无标记引用，本次精确删除；`card-box.wxss` 里仍在使用的同名 `selection-toolbar` 规则未改动。

## 2026-09-15｜知识卡卡集页操作栏吸顶

- 发起人：产品负责人
- 负责人：Codex
- 状态：已确认并实现
- 新增决议：DEC-049

产品负责人反馈：卡集页长按卡片后出现的黑色操作栏（编辑/添加/删除/移动/置顶/取消）下滑页面时不会吸顶，而是留在很上方。原因是该操作栏用 `position: sticky; top: 16rpx` 吸顶，基准落在固定导航栏（不透明、`z-index:30`）背后，同时真机上表现为整条滚走。

第一版修复把它改成固定吸在导航栏下方，但产品负责人指出“一滚动就瞬移到顶部”太生硬。最终口径：操作栏默认出现在所按卡片或目录标题的**上方**（上方空间不足时出现在下方，并限制在视口内），出现后**跟随内容一起滚动**——向下滚时随内容逐渐上移，滚到顶部导航栏下方才停住并保持可见，向上回滚时随内容一起下移回到原位。

操作栏是浮层，不占用文档流，出现和消失都不得让卡片内容改变位置；横向位置保持原规则（多选按所选卡片所在列左/中/右对齐，目录整理居中）。多选过程中每点选一张新卡片，操作栏移动到该卡片上方并从新位置继续跟随滚动；取消选择某张卡片时保持原位。目录整理操作栏与多选操作栏共用同一条规则。由于小程序原生 `sticky` 在这一页不可靠，跟随与吸顶由 `onPageScroll` 计算文档位置实现。

同时把该页的顶部基准变量从 `catalogPanelTop` 统一更名为 `floatingTop`，目录抽屉与操作栏共用。

1. Agent 1 只读取 `active` 档案的规范名称和别名，用于术语标准化，不读取完整边界覆盖独立特征提取；

4. Agent 4 可读取 `active` 和待核版本以提交增量，但不能激活档案；
5. 编译 Agent 读取教材原文、上一 `active` 版本和草稿；
6. 核验 Agent 读取草稿、上一 `active` 版本和原始教材证据，只给核验意见；
7. 用户推荐链路只能读取 `active` 档案。

RAG 提供教材原文事实；知识档案提供概念边界和稳定引用，不能替代原文证据。

### DEC-009｜教材变化按事实声明精确失效【已确认】

档案同时保存教材文件版本和哈希、OCR/正文知识库版本、目录版本，以及每条引用片段的 ID、标准化文本哈希、页码位置和所支撑的事实声明。

### DEC-010｜正式关系与审核状态分离【已确认】

正式概念关系冻结为：

- `is_a`：种属关系，有向；
- `part_of`：整体与组成关系，有向；
- `prerequisite_for`：前置知识关系，有向；
- `supplements`：补充说明关系，有向，不自动进入最小充分知识集；
- `contrasts_with`：对比关系，双向；
- `confusable_with`：易混关系，双向。

`is_a`、`part_of` 和 `prerequisite_for` 必须检查有向环。上位/下位等反向名称由查询派生，不重复保存两条事实。

“同概念候选”和“不确定”属于审核状态，不是正式关系。确认同义后合并档案或登记别名；确认前不得当作同一概念参与正式分类。

教材原文与证据、受影响题族、教材出现位置、独立核验详情和原始 JSON 默认折叠；原始 JSON 仅作高级只读排障视图。内容或证据变化后旧审核结论自动失效；所有审核单元完成通过并绑定有效证据前，档案不得激活。

正式关系只连接实际存在的知识档案 ID。目录层级由教材出现位置承担，不能用目录名、目录节点 ID、书目 ID 或占位 ID 代替概念关系目标。

### DEC-018｜重复题合并为规范题，源题离线并保留历史【已确认】

重复题合并必须先由人工明确一个规范题和一个或多个源题。规范题继续承载后续练习与维护；源题只改为离线合并状态并保存指向规范题的稳定映射，不得物理删除。规范题可以反查全部源题，映射不得形成自指、循环或多级链。相似题、同类题和变式题不是重复实体，不进入本合并流程。

合并默认不拼接或覆盖题干、选项、答案、解析、来源和教材证据。面向未来的题族成员、知识归属以及已经登记支持合并的其他活跃关系应迁移到规范题；目标已有同一关系时幂等折叠。关联题族可以去重后并入，但全局仍只能保留一个主题族；规范题与源题主题族冲突时必须由人工裁决，未裁决不得提交。发现未纳入迁移协议的活跃引用时也必须阻断，不允许先下架源题再留下悬空关系。

历史作答、历史巡检、旧审核记录和操作日志继续绑定原题 ID 与当时版本，不得改写历史事实。源题离线后不再进入前台题库、新练习或新的管理选择，但仍可在后台审计中查看，并可通过映射打开规范题。若需要把源题内容吸收到规范题，必须另行执行版本化题目编辑，不能借关系合并静默覆盖权威内容。

执行补充：合并源题属于终态归档，不能继续显示在“未成族题目”，也不能提供普通编辑、恢复、重新归组或永久删除。活动列表默认过滤合并源题，精确审计查询仍保留原题及版本；普通永久删除同时禁止删除合并源题和仍被源题指向的规范题。离线设备迟到上传的活跃复习状态与收藏按映射收敛到规范题，历史作答、复习和评分记录仍保留原题 ID。合并错误只能由未来独立的“撤销合并”协议处理，不能用普通恢复破坏映射和历史链。

本操作采用独立的 `QuestionMergeCommitV1`：提交保存稳定 `commitId`、请求哈希、操作者、原因、规范题与源题版本、关系基线、迁移计划和主题族裁决。服务端先完成版本、范围、映射、循环、关系完整性和唯一主题族校验，再一次性迁移并去重活跃关系、推进题族成员修订、使受影响题族与建议待复核、写入映射和操作日志，最后才将源题离线。任何一步失败都不得产生部分结果。

文件模式必须先保存覆盖全部相关 Store 的 `prepared` 快照，支持整体回滚、启动恢复和同请求幂等重放；相同 `commitId` 用于不同请求时返回冲突。PostgreSQL 必须使用同一事务或经过验证的等价一致性方案。管理端在提交前展示关系影响和冲突裁决并二次确认，操作日志完整记录迁移、去重、失效、失败、回滚与恢复结果。真实数据只能经正式 API/Store 修改，执行前后保留可核验快照和哈希，不直接编辑运行文件。

- 发起人：产品负责人
- 负责人：Codex（题族、巡检与知识档案协同）

### DEC-020｜题族事实、目录展示与 Agent 经验分层治理【已确认】

#### 一、题族采用六维语义定义

正式题族同时维护名称、唯一核心知识 `coreKnowledgeNodeId`、包含核心知识的作答必需知识 `requiredKnowledgeNodeIds`、可多选教材锚点 `textbookAnchorNodeIds`、考查动作 `assessmentAction`、纳入与排除边界 `inclusionBoundary` / `exclusionBoundary`。教材锚点首项兼容旧 `knowledgeNodeId`。

题族的同一性按“相同核心知识组合（核心知识 + 作答必需知识） × 相同考查动作 × 相同辨析边界”判断。名称、教材路径、关键词、`focusKey` 或题干相似只能用于召回，不能单独证明同族。题族页必须明确展示核心知识、作答必需知识和教材锚点。

#### 二、候选新题族必须经过人工创建闭环

Agent 3 找不到符合六维定义的现有题族时，提交候选新题族草稿。草稿必须含名称、教材锚点、核心知识、作答必需知识、考查动作、纳入边界、排除边界、教材证据和相似题比较。审核员可以逐字段修改、确认创建并归入、驳回或保持待定；只有人工执行“确认创建并归入”后才产生正式题族和成员关系。AI 不得直接建立正式题族，未确认题目继续待归组。

#### 三、用户端目录改为教材骨架上的主题族投影

用户端目录使用教材知识树提供科目、教材、章、节和知识小点骨架，只投影已确认题族。题目只随唯一主题族的教材锚点投影；关联题族和题目自身知识标注只作关系、教研解释、筛选和 Agent 判断，不增加目录投影。同一主题族有多个教材锚点时可以在对应分支形成入口，但所有入口始终指向同一个题目实体。

父目录递归汇总全部下级，数量和题目列表按稳定题目 ID 去重。题目属于多个题族、拥有多个知识标签或关联到跨章节题族时，在同一统计范围内仍只计算一次。待审核、已驳回和候选新题族不进入正式用户目录。

#### 四、题族集与动态关系分工

题族集只保存明确、稳定且需要人工组织的训练主题树。易混、前置、相似、跨章节和共同案例等多维关系，依据题族知识标签、教材锚点、考查动作、边界和已确认案例动态计算，不全部手工塞进题族集树。动态关系必须展示依据和置信状态，不自动改变题族集直属关系或题族六维事实。

#### 五、四 Agent 职责

1. Agent 1 独立提取题干关键词、每个选项涉及的候选知识、解题依赖及顺序、主次、跨题族概率和调用深度。对“以下哪个说法正确/错误”等题逐项判断：通常提高正确项权重；若多个干扰项共享同一知识且辨析它们构成主要机制，共同知识可以成为主判断。正式知识仍须通过最小充分知识集的删除检验，不能见词全收。
2. Agent 2 根据 Agent 1 特征，结合知识树、`active` 档案边界、已确认题族和人工确认/改判案例检索候选。规则库只作冷启动、例外补丁与兜底；案例充足后主引擎逐步切换为向量和确认案例召回。
3. Agent 3 回教材原文独立核验知识是否存在、档案边界是否有证据、题目是否属于候选题族，以及题族真实成员相似度。结果可以是加入已有题族、候选新题族草稿、待归档或待归组，不能自动落库。
4. Agent 4 先保存每次人工确认或改判为审核事件。同类问题累计至少 3 个独立案例后，才允许生成规则草稿或档案修订建议；单个案例不得直接泛化成规则。

#### 六、Agent 4 正负向沉淀

正向确认后保存关键词、依赖项、最终知识与题族归属，进入后续检索和向量素材；发现与现有规则冲突时只登记例外案例，不自动修改规则。负向改判保存“题目、Agent 2 原建议、人工最终结论、审核员原文理由”，保留原文而不强写成规则；后续相似题检索时作为高权重参考案例。同一反馈主题优先补充已有草稿，必要时才新建规则。

规则草稿、已启用规则和已停用规则均可由人工发起删除。删除保留操作者、时间、原因和原规则快照；已启用规则删除前必须明确提示，确认后立即退出后续巡检。规则、知识档案和候选新题族均不能由 Agent 自行批准。

#### 七、题目标签与专项训练

题目编辑增加多选 `examTags`，稳定值为 `insert`（插本）与 `graduate`（考研），迁移期兼容旧 `examTrack`。题目知识标注不承担目录投影职责。

专项训练首先使用题目的主题族。系统能够知道用户选错选项涉及的知识，但不能仅凭一次错误准确知道原因：错误选项知识与主题族核心/必需知识相同时，简单推荐主题族；分属不同知识时，依据确认题族的知识标签和人工案例动态计算候选训练关系；证据不足时回退到主题族或明确显示证据不足，不得把选项出现的全部知识都推送。

#### 八、知识档案正文与动态计算边界

知识档案正文继续由人工维护定义、纳入/排除边界、教材证据与出现位置。档案页动态计算对应题族、所属题族集、已覆盖考法、无题族考点形成的题库缺口，以及缺少充分教材依据的题族审核风险；动态结果不写回正文版本。知识档案可以辅助 Agent 1-3、题目完善和 AI 补充答案，但不能替代教材原文、来源答案或人工审核。

#### 九、当前实现边界

本决议分阶段落地。六维题族字段及管理界面、候选题族草稿、目录投影、动态题族关系、考试标签和规则删除以实际代码与专项测试结果为准；完整四 Agent 持久化学习闭环、向量优先匹配、选项到知识的稳定诊断映射、PostgreSQL 生产事务和全量知识档案激活仍未完成，不能对外宣称已经形成成熟的自动教研或精准错因诊断系统。

### DEC-023｜题族语义确认与训练样本充足度分离【已确认】

`confirmed` 只表达题族的核心知识、作答必需知识、教材锚点、考查动作等语义事实，以及题目归入该题族的关系已经经过人工确认；它不承诺题族已经拥有足够的同类题、变式题或完整训练梯度。不得继续用“至少两道题”替代题族语义审核。

普通人工确认的成员门槛如下：

1. 题族至少有 1 道真实成员题，并且必须且只能保留 1 道原型题；
2. 只有 1 道成员的题族允许确认，确认后显示“已确认 · 单题待扩充”或等义的“样本不足”提示；后半部分是动态质量标记，不新增第四种题族审核状态；
3. 0 道成员的空题族只用于预建题族骨架，不能确认；
4. 不得复制同一道题、把相近但不同考查动作的题强行合并，或放宽核心/必需知识与边界来凑成员数量。

单题题族确认后可以作为唯一主题族投影到用户教材目录，也可以用于题族归因、原题复习、延迟复测和 Agent 的已确认候选检索。Agent 面对仅有一个样题的题族时仍须结合六维题族事实、教材证据和题目全部选项重新核验；单个样题不能独自证明新题必然同族。

训练能力不再随题族确认状态一次性全开，而是按真实额外成员分别判断：

- 同类训练：排除当前题后，存在至少一道可用的原型题或同类题才启用；
- 变式训练：排除当前题后，存在至少一道可用的变式题才启用；
- 缺少某类额外成员时只禁用对应入口，并显示“暂无其他同类题”或“暂无其他变式题”；仍可回退到原题延迟复测，不得跨题族硬凑；
- 后续加入、移出或修改成员仍按既有规则使题族退回待审核，重新确认后再按最新成员动态计算训练能力。

管理端单题题族的主按钮使用“确认单题题族”，确认前说明“确认后进入教材目录与原题复习，暂无其他同类/变式题”；确认后以“已确认 · 单题待扩充”展示。成员摘要分别显示原型题、同类题与变式题数量，不再用“保存题族”无解释地把单题提交降回待审核。

前端提交状态、服务端确认门槛、知识档案派生风险和回归测试已经按本决议完成：单题主按钮为“确认单题题族”，1 题且恰好 1 个原型题可确认，0 题或没有原型题仍被拒绝，确认后的列表显示“单题待扩充”。用户侧完整同类/变式推荐闭环仍属规划能力，后续实现时必须继续依据真实额外成员逐项启用，不得把本次确认能力误写成训练库存已经充足。

## 2026-08-31｜题库归组统计口径

- 发起人：产品负责人

- 状态：已确认

### DEC-024｜归组状态以有效主题族目录投影判断【已确认】

归组统计不再用“题目是否存在任意题族关系”作为唯一判断条件，而以题目能否通过有效、已确认的主题族关系形成教材目录投影为准。统计范围限定为当前教材有效题，并按稳定题目 ID 去重；离线题和已合并源题不参与统计。

1. **已归组题目**：当前教材有效题中，已经形成有效、已确认主题族目录投影的题目。同一主题族即使具有多个教材锚点，同一道题也只计一次。
2. **待归组题目**：当前教材有效题中，没有形成有效、已确认主题族目录投影的题目。它既包括完全没有题族关系的题，也包括只有待审核、已驳回、失效、缺少有效锚点或非主题族关系的题。
3. **无题族关系**：待归组题目的子集，专指当前没有任何题族成员关系的题目；它承接原“暂未成族/未成族题目”的管理含义，但不得继续代表全部待归组。
4. 在同一统计范围内，“已归组题目 + 待归组题目 = 当前教材有效题”，两者互斥；“无题族关系”不得另加到待归组总数上，避免重复计数。

#### DEC-024 实现清理：退役旧待归组活动索引

人工逐项只提供三种结论：

1. **仅使用题目知识**（`question_only`）：该项只需要题目已经确认的核心知识与最小充分知识集来验证或排除，不另存选项知识；
2. **另有选项知识**（`option_specific`）：该项存在能够单独归因的概念、规则或辨析知识，选择后才展开可搜索知识选择器，并至少选择一个节点；
3. **暂无法判断**（`undetermined`）：现有证据不足，允许保留不确定性且不强制选择知识；只排除该项的知识映射指标和错因推断，不自动让整题答案、核心知识、最小充分知识集和题族金标失去计分资格。

系统另保留 `unreviewed` 作为导入、迁移或尚未人工处理的第四种内部状态。它不显示为人工可选项，也不能与“暂无法判断”混用：前者表示工作未完成，后者表示人工已经确认当前证据不足。非争议提交时每个选项都必须完成角色与三态关系判断；整题明确选择“存在争议”时，才可按原规则冻结为 `gold_needs_review`。

### 字段与迁移口径

- 逐项保存 `role`、`knowledgeRelation`、`knowledgeNodeIds` 和可选的 `uncertaintyNote`；
- `option_specific` 要求知识列表非空；`question_only` 与 `undetermined` 要求正式知识列表为空。关系改变后必须清掉不合法的旧 ID，不能只在界面隐藏；
- 旧非空知识列表只在其原来源层兼容为 `option_specific`；旧空列表一律迁移为 `unreviewed`，不猜测审核员原意；
- AI 候选、正式基线和人工金标继续遵守 DEC-033 的分层与后揭示规则，旧 AI 知识不得迁进人工首次判断；
- 新冻结快照逐项保存知识关系。旧不可变快照不补写、不改哈希，缺少关系字段的选项不参加新增加的关系准确率或选项知识节点指标。

### Agent、诊断与指标

- Agent 1 先判断 `question_only / option_specific / undetermined`，仅在第二种状态下输出选项知识及依据；Agent 2/3 不得为填满字段强制补点；
- 用户错选 `question_only` 选项时，系统回退题目核心/必需知识与主题族；只有已确认 `option_specific` 才能进一步使用选项知识做候选归因；`undetermined` 明确提示选项级证据不足；
- 盲测把“知识关系判断准确率”和“选项知识节点精确率/召回率/F1”分开。前者只统计人工确定的 `question_only`、`option_specific`，后者只统计 `option_specific`；`undetermined`、`unreviewed` 均不进入选项知识节点指标。

### 本题裁决示例

“下列各项中，两个音节的声母按清浊音顺序排列的是（ ）”中，A 诗歌、B 酷热、C 美丽、D 医生只是应用同一题目层清浊判断规则的材料。若教材核对未发现某项还需要另一条可单独归因的知识，则四项均选择“仅使用题目知识”，B 保留正确项角色，A/C/D 保留干扰项角色；题目层继续记录声带是否振动/清浊判断相关的核心知识与最小充分知识集。

## 2026-09-02｜题目知识来源分层、题族兼容与目录同源统计补充

- 发起人：产品负责人
- 负责人：Codex
- 状态：已确认，本次显示与同源统计整改已完成
- 关联口径：DEC-015、DEC-024、DEC-033；产品手册 4.1、4.6.1、4.10、4.11、6.2、8.2
- 说明：本条明确既有领域事实和统计口径，不新增重复或冲突的产品决议

### 一、题目知识来源不得混层

同一道题至少存在三层不同来源：当前题目版本保存题干、材料、选项、正式答案、解析和来源等正式字段；人工确认并绑定该版本的 `confirmed` 知识指纹保存核心考查知识与作答最小充分知识集；Agent 的 AI `suggested` 只保存候选节点、依据和置信信息。三者必须分别返回、分别标明来源和状态，不得通过服务端覆盖、页面兜底或默认选中合并成一个“当前值”。

题目正式字段与 `confirmed` 指纹在待复核期间允许暂时冲突，但页面必须如实显示并提示人工处理。没有 `confirmed` 指纹时显示“知识指纹待确认”；不得拿 AI `suggested`、题族定义或教材目录节点补成正式指纹。AI 候选只有经过正式人工审核后才能形成新的 `confirmed` 指纹，不能因它与答案或题族看起来一致就自动晋级。

题族成员页必须展示成员题目当前版本的真实正式字段和 `confirmed` 指纹，同时把所在题族的核心知识、作答必需知识、考查动作和教材锚点标为独立的“题族定义”。以“淼、磊的造字法”题为本次回归案例：当前题目 `v3` 的正式知识字段是“会意”，知识结构 Store 没有 `confirmed` 指纹，另有核心为“象形”的 AI `suggested` 候选，所在主题族定义为“会意”。页面必须分别显示这三层事实，不能把 AI 候选或题族定义冒充正式指纹。

### 二、题族关系不拥有题目版本

归入、移出、移动题族或在主题族与关联题族之间调整，只改变题族成员关系、训练角色和对应关系修订号，不自动改写题目正式字段、`confirmed` 知识指纹或 `question.version`。如果人工判断题目知识确实错误，必须走正式题目编辑与审核流程形成新版本，并按既有规则使受影响题族和旧审核结论退回待复核；不能借题族关系操作静默同步题目知识。

题族兼容按三个角色判断。主题族是题目唯一主要训练归属，题族核心知识应等于题目 `confirmed` 核心知识，但题族作答必需知识可以只是整题最小充分知识集的一部分。作答必需关联题族允许拥有不同核心知识，其核心与必需知识必须被题目知识集覆盖并通过删除检验；主题族与全部作答必需关联题族的必需知识并集必须完整覆盖整题。普通关联只保存相似、易混、前置或教研参考关系，不参与联合覆盖和专项训练。缺少 `confirmed` 指纹时只能标记兼容性待确认，AI `suggested` 不得替代人工裁决。

### 三、目录左右统计使用同一投影集合

题库教材目录的正式题数只由四项门槛共同决定：题目是当前教材有效题，题族为 `confirmed`，成员关系为 `confirmed` 的唯一主题族关系，题族拥有当前教材内仍有效的教材锚点。通过门槛的题目投影到每个有效锚点，并向所有祖先目录递归汇总；每个目录范围按稳定题目 ID 做集合去重。题目知识指纹、AI `suggested`、关联题族、待审核或已驳回题族、待审核关系和无效锚点均不参与。

管理端左侧目录徽标与右侧所选目录的“正式投影题数”必须读取同一份递归去重后的题目 ID 集合，筛选范围、子树范围和四项门槛完全一致。右侧若展示“全部状态”“仅当前节点”或题族成员关系总数，必须另设名称和数字，不能与正式投影混用；多个题族卡的成员数也不能直接相加替代去重后的目录题数。

### 四、题目编辑为主要入口，题族页只读比对

题目编辑页是人工查看、修改和提交题目正式知识指纹的主要入口。题族成员区仍可在当前统一工作区内直接查看题目，但其指纹区域只负责比对：题目正式指纹和题族指纹分别只读展示，AI `suggested` 候选另列为未确认。题族页不得把 AI 候选或题族指纹渲染成题目正式指纹，也不得在确认题族时顺带写回题目知识。

题目编辑是主要人工界面，但不是唯一可以发起正式业务同步的页面。金标审核、巡检采纳等入口如果经过人工裁决需要修正题目知识，只能调用与题目编辑相同的正式领域命令、版本门禁和审计协议，不得各自直接改写知识结构 Store。这样统一的是写入协议，而不是强迫审核员离开当前工作流后重复操作。

## 2026-09-02｜跨知识题改为多题族联合覆盖

- 发起人：产品负责人
- 负责人：Codex
- 状态：已确认，已实现
- 新增决议：DEC-037
- 取代范围：DEC-036 中“主题题族或候选新题族必须独自等价整题最小充分知识集”的解释；DEC-036 的派生版本改层级、人工确认和不可变父快照规则继续有效

跨知识题的题目级最小充分知识集可能天然大于任一单独题族的作答必需知识集。题族回答的是一种稳定考查方向，不能要求其中一个主题题族独自承载整道题调用的全部知识。后续语义门禁以题族联合覆盖为准：主题题族核心仍须对应题目核心知识；主题题族自身必需知识可为整题知识集的真子集；主题题族与全部“作答必需”关联题族的必需知识并集必须完整覆盖整题最小充分知识集，且任何贡献题族不得引入题目知识集之外的必需节点。

关联题族拆成两个明确角色：`required` 表示通过删除检验、确实参与可靠作答，参与联合覆盖、专项训练和盲测题族集合计分；`reference` 表示相似、易混、前置或教研参考，不参与覆盖和计分。旧记录只有 `relatedFamilyIds` 时，为保持此前“关联即作答必需”的产品语义暂按 `required` 读取；再次人工审核时必须允许逐项改判。结构化保存以 `relatedFamilyRelations[].coverageRole` 为准，`relatedFamilyIds` 仅作为兼容 ID 集合保留。

无匹配题只表示没有可用的现有主题题族，不表示所有关联题族都不存在。因此 `create_new` 可以保存“候选主题题族 + 现有作答必需/普通关联题族”；页面切换到无匹配时只清空现有主题题族，不得清空已经成立的关联选择。盲测遮蔽也只隐藏候选主题题族的语义等价项，现有作答必需关联题族应继续留在候选上下文中供 Agent 判断。

若相同知识组合与相同考查动作在多个独立题目中稳定重复，可以再建立跨知识综合题族；偶发组合优先使用多个作答必需题族联合归属。删除某个必需关联题族后知识节点仍被其他题族覆盖时，系统只提示冗余风险，不直接阻断，因为不同题族可能在同一知识节点上承担不同考查动作，最终仍需结合删除检验人工裁决。

- 取代范围：此前“任一题目内容、成员或题族归属变化都让整个题族退回待审核”的宽泛失效规则

题族是否成立和某道题是否适合归入该题族是两层事实。题族原有 `pending_review / confirmed / rejected` 三态只表达六维定义是否经过人工裁决；逐成员关系另设 `pending_fit / confirmed` 审核状态。题族定义没有变化时，新增、移除、移动成员，修改某道成员题的题干、选项、答案或正式知识指纹，以及调整该题的主题族/关联题族，只精确失效该题涉及的成员关系，不得把整个已确认题族及其稳定旧成员反复打回待审核。

只有核心知识、作答必需知识、教材锚点、考查动作或纳入/排除边界等题族六维定义发生实质变化，才重开题族定义审核并重新校验全部成员。来源、标签、难度、排版、题族说明、排序和题族集组织等不影响题族适配的变化不得触发整族失效。

用户侧正式目录、专项训练、智能复习、统计、案例检索和盲测上下文只能消费“题族定义已确认 + 成员归属已确认 + 题目有效”的关系。已确认题族包含新增或变化成员时，管理端显示“已确认 · N 个成员待审”，并允许直接筛选和连续审核这些成员。删除最后一个已确认有效成员或唯一原型题归属失效时，题族定义仍可保留已确认，但派生为暂无可用成员并暂停用户侧消费；该提示不是新的题族审核状态。

旧数据没有成员审核状态时，已确认题族中的既有成员按 `confirmed` 迁移读取，待审核或已驳回题族中的成员按 `pending_fit` 读取。后续保存必须显式落库成员状态，并分别维护题族定义版本与逐题成员归属修订，保证批量导入后只审核新增题目的归属，而不重新审核已经稳定的题族。

实现补充：首次确认从未审核题族时，可在同一次人工动作中确认当前成员；已确认题族新增成员，或题族六维定义重开后再次确认时，不得借题族确认批量扫过成员待审状态。管理端已提供成员归属筛选、逐题确认与驳回，题族标题显示待审成员数；驳回只删除该成员关系，不改变题族定义状态。

正式消费统一要求“题族定义已确认 + 成员归属已确认 + 存在有效已确认原型题 + 题目有效”。用户目录、题族关系、知识档案覆盖统计、Agent 校核及未来金标派生均使用同一门禁；待审、下线、已合并成员不得污染正式题数、覆盖考法或题族事实。文件与 PostgreSQL 模式均已接入成员审核和回滚恢复协议。

验证结果：后端及相关接口定向测试 `211/211` 通过，正式消费者专项联跑 `49/49` 与金标 API/知识档案联跑 `15/15` 通过，全量测试 `858/858` 通过。未修改 `.runtime` 正式数据，未改写冻结金标，也未运行盲测。

## 2026-09-03｜题目知识焦点、题族判别范围与成员贡献分层

- 发起人：产品负责人
- 负责人：Codex
- 状态：已确认，已实现首版，待正式数据迁移预演与人工验收
- 新增决议：DEC-039
- 取代范围：DEC-020 中把题族核心知识、题族作答必需知识和教材锚点混成一组固定题族指纹的解释；DEC-037 中直接用题族整体必需知识参与逐题联合覆盖的解释
- 保留范围：DEC-026 的删除检验与不得自动补写知识、DEC-037 的多题族联合覆盖方向、DEC-038 的题族定义审核与成员归属审核分离继续有效

“下面的词属于单纯词的有”暴露出当前门禁无法同时表达两种真实情况：跨知识题的整题最小充分知识集可以大于任一单个题族；反过来，一个稳定的分类题族也可以覆盖多个互斥兄弟知识类别，而其中某一道成员题只聚焦一个类别。当前系统把题目“单纯词”与题族父节点“词的结构类型”做精确相等比较，又直接拿题族整体必需知识参与联合覆盖，因此出现“主题核心不一致”和“超出范围”。按旧手册该提示是规则的真实执行结果，不是单纯页面错误；把题目知识强行上提到父目录只会损失题目归类精度。

正式分层如下：

1. **题目知识焦点**：一道题唯一、最直接询问的知识节点；历史“核心考查知识/题目核心知识”按此兼容。它必须属于本题作答的最小充分知识集，但不决定题族范围或用户目录。
2. **题目最小充分知识集**：可靠作答实际必须调用的最小节点集合，只能由正式答案、教材证据和删除检验确定。题族覆盖多个知识或选项出现多个名词，均不得反向扩写本题知识集。
3. **题族判别焦点**：同族成员共同使用的稳定判别规则或训练能力，例如“依据语素构成区分单纯词与合成词”。它是题族语义中心，不能由教材父目录、题族名称或通用“概念识别”动作代替。
4. **题族覆盖知识**：该判别任务允许承载的明确知识节点集合，可以大于任一道成员题的最小充分知识集。覆盖范围是人工确认的题族定义，不能随着新成员加入自动扩张。
5. **题族范围锚点**：题族在教材骨架中的唯一组织、检索和用户目录投影位置。系统可以根据覆盖知识的最近共同父节点提出候选，但必须人工确认；父子或共同祖先关系不能证明同族，也不参与作答知识覆盖。多个实际教材位置另存为教材证据锚点。
6. **成员贡献知识**：某一道题以主题族或作答必需关联题族身份归入时，该关系实际承载的本题最小充分知识子集。它属于逐成员归属事实，不属于题族整体定义。

兼容门禁统一为：题目知识焦点必须属于题目最小充分知识集；主题成员和作答必需关联成员的贡献知识必须非空，并同时属于题目最小充分知识集与各自题族覆盖知识；主题成员贡献必须包含题目知识焦点，且题族判别焦点、考查动作和纳入/排除边界适用于本题；全部主题/必需成员贡献并集必须与整题最小充分知识集按规范节点集合等价。普通关联不保存用于覆盖的贡献知识。任何父子、祖先、同章或共同范围锚点关系都不能替代这些校验。

同一判别规则下的互斥兄弟类别可以组成一个题族。例如“单纯词与合成词识别”可把二者作为题族覆盖知识，把“词的结构类型”作为范围锚点，并把“依据语素构成区分单纯词与合成词”作为判别焦点；某道“哪些属于单纯词”的题目知识焦点仍可保持“单纯词”。该题的最小充分知识集是否还包含“合成词”，必须单独通过删除检验，不能因为题族覆盖二者而自动加入。相反，只是在一道题中偶然共同出现、但判别规则不同的知识仍应拆成多个题族，并通过逐成员贡献联合覆盖。

DEC-038 的失效颗粒度同步细化：新增成员，或只修改某成员角色、贡献知识及题目内容，只让对应成员进入 `pending_fit`；修改题族判别焦点、覆盖知识、范围/证据锚点、考查动作或边界，才重开题族定义审核并重新校验全部成员。范围锚点由覆盖知识生成候选不等于可以自动写入；共同父节点过高或跨越不相干分支时必须提示人工拆族。

旧 `coreKnowledgeNodeId`、`requiredKnowledgeNodeIds`、`knowledgeNodeId` 和 `textbookAnchorNodeIds` 不得静默改名或原地重解释。后续实现需要新的题族定义协议版本、逐成员贡献字段、迁移预演、人工复核和审计记录。已冻结 V1/V2 金标继续按原协议和原字节解释；新金标与回放上下文必须显式保存新的定义协议版本。本次只修订三份开发手册，没有修改代码、`.runtime`、正式题库、题族关系、冻结快照或 Agent 经验，也没有运行盲测。

实施记录（2026-09-03）：首版代码已使用 `family_knowledge_v3` 显式区分新语义，旧 `family_knowledge_v2` 冻结事实继续走旧分支。题目编辑、题族编辑、AI 巡检、金标审核、候选建族和盲测上下文均已接入独立题族判别焦点与逐成员贡献；成员变化只精确产生 `pending_fit`。前端定向测试 `97/97`、后端相关联跑 `185/185`、全量回归 `872/872` 通过。此次未迁移或修改 `.runtime` 正式数据，下一步只对“单纯词与合成词识别”等真实样本做只读预检和人工迁移验收。

迁移补充（2026-09-03）：V2 修订草稿中的历史题族裁决可能没有协议版本。若该批次尚未冻结且某题已被明确开放“题族复审”，管理端必须直接提供 V3 的逐成员贡献编辑能力，但贡献默认保持为空，只能由人工采用建议或逐项选择；保存时显式写入 `family_knowledge_v3`。冻结 V1/V2、继承完成项和不需要题族复审的记录继续按原协议只读，不得仅凭批次名称、版本号或父快照自动迁移。

交互补充（2026-09-03）：逐成员贡献仍遵守“默认空、人工显式确认”的独立金标口径。即使题目最小充分知识与题族覆盖知识只剩一个相同节点，也不得自动勾选；页面应把显式采用按钮放在贡献选择框旁，唯一候选直接写出节点名，例如“采用‘笔顺’”，多项候选再显示数量。按钮只在审核员点击后写入草稿并刷新联合覆盖，清空后不得自动回填，非题族可编辑状态必须禁用。该快捷操作来自人工值与正式题族值的确定性交集，不是 AI 候选，也不得绕过最终题族人工提交。

## 2026-09-03｜题目知识焦点增加 `core / scope_anchor` 显式角色

- 发起人：产品负责人
- 负责人：Codex
- 状态：已确认，待代码实现与人工数据迁移
- 新增决议：DEC-040
- 取代范围：DEC-039 中“所有题目知识焦点都必须属于最小充分知识集，并由主题成员贡献承载”的无条件规则
- 保留范围：DEC-039 的题目知识、题族定义与逐成员贡献分层，DEC-037 的多题族联合覆盖，以及 DEC-038 的精确成员失效继续有效

题目正式知识指纹继续只保留一个焦点节点，但必须显式说明该节点在本题中的角色。金标答案知识保存 `answerKnowledge.coreKnowledgeRole`，正式题目指纹保存同义字段 `primaryNodeRole`；允许值只有 `core` 与 `scope_anchor`。旧记录缺失角色时按 `core` 解释，以维持当前正式题目、历史审核记录和冻结快照的原语义，不得根据目录位置、题目内容或批次版本自动猜测角色。

`core` 表示题目直接考查的知识。该角色继续遵守原门禁：题目焦点必须属于作答的最小充分知识集，主题题族覆盖知识必须包含该节点，主题成员贡献也必须承载该节点。

`scope_anchor` 只解决跨知识题的范围组织问题。例如一道题同时调用语音和词汇知识，但需要在管理和教研界面给出一个主要范围时，可以由人工把“词汇单位”标为 `scope_anchor`。它不表示作答必须调用“词汇单位”这个父级概念，因此不得自动加入最小充分知识集，不参与题族联合覆盖，也不要求主题题族覆盖或主题成员贡献承载。父子、祖先、共同目录和当前主题族都不能自动证明某节点应成为 `scope_anchor`。

显式角色不会放松成员贡献与联合覆盖门禁。无论题目焦点是哪种角色，主题成员贡献仍须为非空的作答知识子集；作答必需关联成员也必须提供通过删除检验的非空贡献；两者并集必须与题目 `requiredKnowledge / requiredNodeIds` 精确等价，不能遗漏或额外引入节点。普通关联 `reference` 仍不保存贡献知识，也不参与覆盖、专项训练或题族命中计分。

“花蝴蝶儿”当前六项 required 中，“词汇单位”适合作为 `scope_anchor` 候选，而不应仅因范围身份成为联合覆盖分母；“确定语素和词的常用方法”属于较宽的方法总类，也需要结合具体叶子节点重新做删除检验。“语素”“替代法”“音节的结构”“什么是儿化”之间哪些承载独立作答事实、哪些只是同一事实的不同教材证据，仍须人工逐项裁决。此次决议只修正协议，不替人工直接精简这道题。

冻结与迁移边界：金标集 V1 保持原始文件、原始字节、sidecar 和哈希不变，读取时因缺少显式角色继续按 `core` 处理；以后已经冻结的 V2 也不得原地迁移。当前 `.runtime`、正式题目、审核草稿和题族关系均不自动补写角色。只有未冻结记录进入明确的人工修正流程并保存时，才允许形成新的显式角色事实；角色变化属于正式知识指纹变化，应推进题目版本并只精确失效该题的成员关系，不得让题族定义整体退审。

实施边界（2026-09-03）：本次只同步《一、产品手册》《二、变更日志》《三、交流文档》，没有修改代码、测试、`.runtime`、正式题目、题族、审核草稿、Agent 经验、冻结快照或盲测结果。

## 2026-09-16｜V3 冻结后的唯一下一步与固定执行顺序
